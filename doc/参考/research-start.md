**纯 Web 能做出可用的鹰眼原型，做不到转播级毫米精度。** 采集、标定、场地关键点、球追踪、把结果绑到标准 3D 模型，浏览器里都能跑；卡点是多机同步、小物体高速追踪，以及实时稠密 3D。

## 纯 Web 能做到哪一步

| 能力 | 纯 Web | 说明 |
|---|---|---|
| 1～2 路 USB 摄像头 | 可行 | `getUserMedia`，1080p@30/60 没问题 |
| 3 路以上工业/IP 相机 | 需网关 | 浏览器不能直接吃 RTSP/GenICam，要本地服务转 WebRTC |
| 多机硬件同步 | 基本不行 | 没有 genlock/PTP；只能靠时间戳，误差通常几十毫秒 |
| 标定 + 畸变矫正 | 可行 | OpenCV.js（张正友）+ WebGL/WebGPU shader 实时去畸变 |
| 场地特征点 | 可行 | 线/角点检测，或关键点模型（ONNX Runtime Web / TF.js / MediaPipe） |
| 球类追踪 | 半可行 | 慢速、大目标可以；网球/羽毛球这种小、快、糊，30fps 很容易丢 |
| 多视三角测量（稀疏 3D） | 可行 | 经典多视图几何，绑到球场 CAD/标准模型完全可以 |
| 稠密场景 3D（点云/网格） | 很吃力 | 实时几乎不行；离线高斯/NeRF 也偏重，不适合当主链路 |
| 置信度 | 可行 | 检测分数 + 重投影误差 + 多机一致性 |

单机也能做：本质是 2D 检测 + 已知场地平面的单应（homography），球在地面附近时能估平面位置，高度基本靠猜，所以「1 个也行但没那么准」。

**结论：** 训练/回放/演示级鹰眼，纯 Web 够用。转播判罚级（多机、毫米、低延迟）不行，计算可以上 WebGPU，同步和高速采集过不去。

## 推荐架构（按目标分）

**A. 纯浏览器演示（2 机、平面定位）**  
摄像头 → WebCodecs/Canvas → WASM 去畸变 → 检测/追踪 → 三角测量或单应 → Three.js 绑标准球场模型。  
适合：室内慢速球、固定机位、精度到「几十厘米～几厘米」。

**B. 完整功能（建议）**  
边缘机做采集/同步/推理，浏览器只做 3D 展示和标注。Web 端仍是产品界面，只是把重活放在本地进程。这是专业鹰眼的常态。

## 完整功能的硬件和资源

「完整」按业余可用 / 准专业 两档看。

### 业余可用（训练、回放、3D 轨迹）

- **相机：** 2～4 台，1080p、60fps，全局快门更好；对向或正交布置，基线尽量大
- **同步：** 软件时间戳即可（误差 20～50ms，快球会糊成一段弧）
- **电脑：** 近年中端 GPU（RTX 3060 / 4060 或 M 系列），16～32GB 内存
- **浏览器：** Chrome/Edge，打开 WebGPU；模型用 ONNX/WebGPU，单路检测约 15～30fps
- **精度预期：** 标定好、场地已知时，平面误差大约 **3～15cm**；高度更差
- **网络：** 本机或千兆局域网；多路 1080p 编码后大约 10～30Mbps/路

### 准专业（更稳的 3D、更快的球）

- **相机：** 4～8 台，1080p 或 1440p，**120～240fps**，全局快门，固定焦距、低畸变镜头
- **同步：** 硬件触发 / genlock，或 PTP；浏览器吃不到，必须本地采集卡/工控机
- **计算：** 工作站级 GPU（RTX 4080/4090 或同等），或 NVR + 推理盒；多路解码 + YOLO/专用 tracker 并行
- **标定：** 场地控制点 + 标定板；相机固定后定期复标
- **光照：** 均匀、高快门不闪；室内尽量避开工频闪
- **精度预期：** 良好标定下平面 **1～3cm**；高速小球仍可能丢帧
- **存储：** 多路原流很大，通常只存轨迹 + 关键帧，不存全量视频

转播级（十台以上高速机、亚厘米、硬件同步、专用机房）不在纯 Web 范围内，硬件和标定流程本身就是一套系统。

## 纯 Web 落地时的硬限制

1. **USB 带宽：** 笔记本同时 2 路 1080p@60 就容易顶满，第 3 路往往要降分辨率或走网络相机。
2. **内存：** WASM/WebGPU 堆大致数 GB 级，大模型和多路 4K 帧缓存会爆。
3. **帧率：** 浏览器相机流常见 30fps，少数 60；120fps+ 工业相机进不了 `getUserMedia`。
4. **时间同步：** 没有共同硬件时钟，多机 3D 对快球会「对不齐」。
5. **权限和稳定性：** 摄像头占用、后台节流、标签页挂起，不适合当 7×24 采集端。

## 若要做，功能该怎么切

1. **先做 2 机 + 已知场地模型：** 标定、去畸变、场地关键点、球检测、三角测量、Three.js 绑定、输出关键点/置信度。这是纯 Web 的甜点区。
2. **置信度不要只信检测分数：** 加上重投影误差、多机交会角、轨迹平滑残差，丢检时标低置信而不是假 3D。
3. **3D 用「稀疏绑定」而不是稠密重建：** 球场用标准模型，球用点+轨迹，人/器材用关键点或简化刚体。稠密重建当离线增强，不要进实时环。
4. **需要第 3 路或高速机时：** 立刻加本地采集网关（WebRTC 推到页面），页面仍负责可视化。
